OpenLabAI: how the guardrails work

An open-source framework that lets an AI agent plan an experiment and run it on lab robots, without ever letting the agent move hardware on its own.

Scientists often wait on an automation engineer for every protocol change, or have to learn each vendor's software. I was that engineer for years. OpenLabAI lets a scientist describe an experiment in plain language; an agent turns it into a protocol, and a set of guardrails decides whether and when the robot moves.

The design rule is simple: the agent can plan anything, but it can only act through tools that validate the request, check it against the robot, wait for a person to approve, and record what ran.

The eight layers

  1. Structured tools, never raw hardwareThe agent can only call a fixed set of tools, such as read_deck, create_protocol, upload_protocol and start_run. It has no other way to reach an instrument.
  2. The request is validated before a file is writtenProtocol names, well references, step types, volumes, mix cycles and deck slots are each checked. Volumes are compared with the pipette's capacity. If anything is off, nothing is written.
  3. The protocol is checked before anything movesOn the Opentrons OT-2, uploading sends the protocol to the robot for its own analysis and creates a run that sits idle. A second check compares the analysed commands with deck limits. With PyLabRobot, the plan is first simulated with tip and volume tracking, which catches aspirating liquid that is not there or reusing a tip.
  4. A person approves every motionAny tool that moves the robot refuses unless it is called with confirm=true, which stands for a named person approving that specific run. Pause and stop are never gated, because they only make the robot safer. In Slack, the approver's identity is recorded and a lab can require a second person.
  5. Checks fail closedIf the robot's analysis timed out, produced no commands, or the constraint checks could not load, the answer is "do not start". A check that could not run never counts as a check that passed.
  6. The approval is tied to the exact protocolThe PyLabRobot connector's approval token is a hash of the plan and of the commands it generates, so what was approved is what runs. The OT-2 path records the SHA-256 of the uploaded file.
  7. Every action is written to an audit logHome, start, pause, resume and stop are logged with the operator and the protocol hash, so a result can be traced back to exactly what ran and who approved it.
  8. Monitoring and recovery go through a personget_run_status reports the robot's errors and the safe next actions for the run's state. After a failure it sends someone to look at the deck. It never retries on its own.

What the guardrails do not do

  • They do not know the biology. They check volumes, tips and deck layout. Whether a run is scientifically right is still decided by the scientist's acceptance criteria.
  • The approval flag is passed by the agent. The next step is approval the server verifies from outside the agent, such as the Slack button, so the agent cannot approve its own run.
  • Some layers are in review. Fail-closed checks, request validation and the gates on homing and resuming are in an open pull request, not yet merged.
